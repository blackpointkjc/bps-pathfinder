Status key: [x] resolved / [~] in progress / [ ] pending verification

## 0. 2026-08-23 session — security fix + CAD/dispatch fixes
- [x] SECURITY: `sendDailyCompanySummary` no longer broadcasts one shared email/notification containing every employee's name, individually-listed missing items (training gaps, expired certs, report-correction feedback with admin comments), and a full named company ranking to every recipient (BCC'd). Each employee now gets a strictly personal email/notification with only their own outstanding items -- no other team member's data, no ranking, no performance percentage (individual or aggregate) anywhere in recipient-facing content. Company-wide numbers are retained only in the internal AuditLog record.
- [x] CAD: `manageCadUnitAssignment` now notifies the officer behind the assigned unit (`Notification` type `call_assignment`/`call_unassignment`, added to the entity's type enum) instead of only toasting the dispatcher who clicked assign. `GlobalMessageBanner` now surfaces and speaks this notification aloud the same way a property-monitoring call is announced (previously an officer got no indication at all that they'd been put on a call).
- [x] CAD: `CADUnitStatusBoard`'s dispatcher/admin check ("can this user trigger officer distress from the unit board") was missing `dispatch_role`/`is_supervisor`, the actual fields Dispatch Center and Command Dashboard use to grant CAD access. A dispatcher granted access only via `dispatch_role` could open Dispatch Center but never saw the distress-trigger controls. The backend (`manageOfficerDistress`) already supported dispatcher-triggered distress and `OfficerDistressBanner` already announces/sirens any active `OfficerDistress` row CAD-wide regardless of who triggered it -- this was purely a frontend permission-check gap.
- [x] `WelcomeBriefing` no longer silently shows "0" for every category (Teams mentions, announcements, property alerts, etc.) when a source fetch fails; failures are now tracked and surfaced as a visible warning banner with a retry, and logged via `console.error` instead of swallowed.
- [x] `Navigation.jsx`'s scheduled-CAD-partnership sync no longer treats a failed "does this officer already have a Unit row" fetch as "no existing unit," which risked creating a duplicate Unit record on every retry; a failed own-unit lookup now aborts the sync instead of fabricating a new unit.
- [ ] INVESTIGATED, NOT YET REPRODUCED: "dispatch log doesn't create a report in the report center" -- `DispatcherShiftReports.jsx` -> `DispatcherShiftReport.create()` -> `AdminReports.jsx` review/approve queue is fully wired end-to-end in code (fetch, filter-by-status, render, approve/reject) and RLS looks correct. Found `IncidentReportModal.jsx`, a from-a-call incident-report form, that is fully built but never imported/rendered anywhere -- likely dead/unfinished work, and a plausible second thing the user meant. Needs either a specific reproduction (which button, what error) or a decision on whether to wire `IncidentReportModal` into Dispatch Center (it currently posts to an external `sendReportToLinkedApp` integration first, which needs verifying before exposing it).
- [ ] NOT YET SCOPED: "reports submitting is not working" / "admin approval is not working" -- user confirmed this means potentially all report types / all approval workflows (PTO, expense, report review). Too broad to fix blind; needs either reproduction steps or a prioritized subset.
